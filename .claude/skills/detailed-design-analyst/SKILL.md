# 상세설계 분석가 (Detailed Design Analyst)

ISO 26262(기능안전)와 Automotive SPICE 4.1 SWE.3(SW 상세설계 및 단위 구현) 프로세스를 준수하는
상세설계 산출물을 분석·작성하기 위한 방법론이다. 공식 산출물 템플릿이 저장소 `WP_Templates/`에
제공되었으므로, 아래 0절의 템플릿 구조를 그대로 따르고 1~9절은 그 템플릿의 표·절을 채우는 방법론으로만
사용한다. 이 스킬은 `requirements-analyst` 스킬로 작성된 SW 요구사항·Use Case, 그리고 SWE.2
아키텍처 산출물(`ENG-SWE2-001`)을 입력으로 받는다는 전제로 동작한다.

## 0. 산출물 템플릿 (공식 — `WP_Templates/` 기준)

> 상세설계 작업을 시작하기 전에 **반드시** 아래 파일이 저장소에 실제로 존재하는지 Glob/Read로 먼저
> 확인한다. 존재하면 이 절의 매핑과 절차를 그대로 따른다. 템플릿을 찾을 수 없으면 그 사실을 리포트
> 서두에 명시하고 0.3절의 표 구조만으로 임시 작성한 뒤 "⚠ 공식 템플릿 미발견 — 재구성 필요"를 표시한다.

### 0.1 SWE.3(상세설계) 산출물 ↔ 템플릿 매핑

| 산출물 ID(등록부 기준) | 내용 | 템플릿 파일 | 형식 | 승인 버전 |
|---|---|---|---|---|
| `ENG-SWE3-001_SW 상세설계서` | 모듈 분해, 함수 계약, 알고리즘, 상태전이 | `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx` | DOCX | v0.9 |
| `ENG-SWE3-002_상세설계 UML 및 호출관계 원본` | 구현 단위 간 UML/호출관계 다이어그램 | `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio` | DRAWIO | v0.9 |
| `ENG-SBOM-001_Python 의존성·SBOM·FOSS 라이선스 목록` | 구현에 포함되는 외부 패키지·라이선스 목록(SWE.3/SUP.8 공용) | `WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록 템플릿.xlsx` | XLSX | v1.0 |

> **버전 유의사항**: `TPL-SWE3-001`/`TPL-SWE3-002`는 등록부(`PRC-TPL-001`)에 **v0.9**로 표기되어
> 있다 — SWE.1/TRC 템플릿(v1.0)과 달리 아직 확정판이 아니므로, 이 두 템플릿으로 만든 산출물의
> 표지·서두에 "⚠ 템플릿 v0.9(초안) 기준 작성 — 정식 v1.0 배포 시 재검토 필요"를 명시한다.
> `TPL-SBOM-001`은 파일 자체에는 v1.0으로 표기되어 있으나, 이 스킬 작성 시점 기준 `PRC-TPL-001`
> "Template Register" 시트에 행이 등록되어 있지 않았다. 사용 전 등록부를 다시 확인하고, 여전히
> 미등재라면 그 사실을 리포트에 남긴다(형상관리 미비 가능성).

상위 입력(직접 수정하지 않고 참조만 함): `ENG-SWE2-001_SW 아키텍처 설계서`(`TPL-SWE2-001`),
`ENG-SWE1-001_SW 요구사항 명세서`(`TPL-SWE1-001`). 산출물 등록 정보는
`WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`의 "Template Register" 시트에서 확인한다.

### 0.2 파일 사용 절차

1. 템플릿 파일을 복사하고 파일명을 `<산출물 ID>_<산출물명>_<프로젝트/베이스라인>.<확장자>` 형식으로
   바꾼다. 원본 템플릿 파일 자체는 수정하지 않는다.
2. **DOCX(TPL-SWE3-001)**: `docx` 스킬로 열어 표지·변경 이력·작성/검토/승인 상태표를 실제 값으로
   채운다. 각 장 아래 "작성 안내:" 문구는 실제 내용으로 교체하고 안내 문구는 삭제한다. 1~15장 구조(2장
   모듈 분해, 3장 상세 호출관계, 4장 공통 자료형, 5장 핵심 함수 계약, 6장 핵심 알고리즘, 7장 정책
   의사결정표, 8장 상태전이 상세, 9장 Web/API 상세, 10장 오류와 방어 동작, 11장 코딩·검증 규칙, 12장
   단위-요구사항 할당, 13장 구현 경계, 14장 추적성)는 임의로 바꾸지 않는다.
3. **DRAWIO(TPL-SWE3-002)**: 안내 도형(`boundary`, `actor`, `element`, `edge`, `guide`)을 삭제하고
   실제 구현 단위(클래스/모듈/함수), 호출·의존 관계, 입출력 자료형으로 교체한다. 각 요소 라벨에 설계
   ID(0.3절)와 관련 요구사항/시험 ID를 병기한다. 검토본·베이스라인 생성 시 PNG도 함께 내보낸다.
4. **XLSX(TPL-SBOM-001)**: `xlsx` 스킬로 열어 "SBOM" 시트에 실제 사용 중인 패키지를
   `Package | Version | Dependency Type | SPDX | Evidence Type | Evidence Locator | Distribution |
   Remark` 컬럼에 기록한다(런타임/개발 의존성을 구분). "FOSS Review" 시트에 라이선스 검토 결과를,
   "Change History" 시트에 갱신 이력을 남긴다. 실제 패키지 목록·버전은 프로젝트의 의존성 파일(예:
   `requirements.txt`, `pyproject.toml`, lock 파일)에서 확인하고 추측하지 않는다.
5. 표지·저작권 각주는 프로젝트 정책에 따라 유지·교체 여부를 사용자에게 확인하고 임의로 삭제하지 않는다.
6. 채팅 중 빠른 논의·검토용 초안은 이 스킬 1~9절 표기(마크다운 표 + 함수 계약 서술 + Mermaid/PlantUML)로
   먼저 제시해도 되지만, **정식 산출물(베이스라인 대상)은 반드시 위 공식 템플릿 파일로 만든다.**

### 0.3 설계 요소 행(표) 공통 속성

TPL-SWE3-001의 관련 장(2·5·6·7·8·12장) 표에는 최소한 다음 컬럼을 포함한다(등록부의 필수 내용
"함수 계약, 알고리즘, 상태전이"를 이 스킬의 품질기준으로 확장한 것):

`설계 ID | 구분(모듈/함수/알고리즘/상태전이/정책표) | 상위 아키텍처 요소 ID | 상위 요구사항 ID |
책임/계약 요약 | 사전조건 | 사후조건 | 예외/오류 처리 | ASIL(해당 시) | 검증수준/방법(단위/통합) |
하류 추적(소스 파일·함수, 단위시험 ID) | 상태`

설계 ID 체계는 `DES-<모듈/컴포넌트>-<일련번호>`(예: `DES-CHILDLOCK-001`)를 기본으로 하되, 프로젝트에
이미 다른 접두어 체계가 있으면(예: 아키텍처 요소 ID 접두어를 그대로 확장) 새 체계를 만들지 말고 그
체계를 잇는다.

## 1. 설계 품질 특성 (IEEE 1016 설계 기술 관행, A-SPICE SWE.3과 정합)

모든 설계 요소는 아래 특성을 만족해야 한다. A-SPICE SWE.3은 상세설계가 아키텍처와 일관되고, 구현·단위
시험이 가능한 수준으로 상세화되도록 요구한다(정확한 BP 목록은 공식 PAM 참조).

| 특성 | 의미 | 점검 방법 |
|---|---|---|
| 정합성 | 상위 아키텍처 요소·요구사항과 모순되지 않는다 | 각 설계 요소에 상위 아키텍처/요구사항 ID 필드 필수(0.3절) |
| 명확성(모호하지 않음) | 함수 계약·알고리즘이 한 가지로만 해석된다 | 2절의 함수 계약 서술 패턴 사용, 모호어 금지 |
| 완전성 | 할당된 요구사항/아키텍처 요소마다 대응하는 설계 요소가 있다 | 12장 단위-요구사항 할당표로 커버리지 확인 |
| 일관성 | 다른 설계 요소·명명 규칙과 모순되지 않는다 | 7절 일관성 점검 절차 수행 |
| 단일 책임 | 함수/모듈 하나에 하나의 책임만 담는다 | 함수가 여러 무관한 책임을 겸하는지 점검 |
| 구현가능성 | 현재 언어·플랫폼·라이브러리로 구현 가능하다 | 담당 엔지니어 확인 근거 기록, 13장 구현 경계와 정합 |
| 검증가능성 | 단위시험(화이트박스)으로 참/거짓 판정이 가능하다 | 5절 참조, 실행 불가능한 검증방법 금지 |
| 추적가능성 | 상위(요구/아키텍처)·하류(코드/단위시험)와 양방향으로 연결된다 | 8절 추적성 방안 준수 |

## 2. 명확성 확보 — 함수 계약 서술 패턴(Design by Contract)

모든 함수/모듈 설계는 다음 구조로 서술해 모호함을 없앤다(요구사항 스킬의 EARS 패턴에 대응하는 설계
버전).

```
함수/모듈: <이름>(<입력 파라미터: 자료형, 단위, 범위>) -> <출력: 자료형, 단위, 범위>
사전조건(Precondition): <호출 전 성립해야 하는 조건>
사후조건(Postcondition): <정상 종료 시 보장되는 결과>
불변조건(Invariant, 해당 시): <실행 전/후 항상 유지되는 상태>
예외/오류 처리: <위반 시 반환값·예외·오류코드와 시스템 반응>
시간/자원 제약(해당 시): <최대 실행시간, 메모리, 스택 등 정량 기준>
```

- "적절히", "충분히", "가능한 한" 같은 모호어를 쓰지 않는다. 경계값·정량 기준(수치, 단위, 한계값)으로
  대체한다.
- 상태전이 설계(8장)는 `<상태>에서 <이벤트/가드>가 발생하면 <전이 동작>을 수행하고 <다음 상태>가
  된다`로, 정책 의사결정표(7장)는 `조건 조합 → 우선순위 → 기대 동작 → 충돌 해결 규칙` 열로 각각
  모호함 없이 서술한다.
- 함수 하나에는 하나의 사전조건 집합·하나의 사후조건 집합만 담는다. 서로 다른 책임이 섞여 있으면
  함수를 분리한다.

## 3. UML/SysML 표현

설계 요소는 표(0.3절)와 함수 계약(2절) 서술에 더해, 이해를 돕는 다이어그램을 포함한다.

| 표현 대상 | 다이어그램 유형 | 권장 문법 |
|---|---|---|
| 모듈/클래스 구조, 속성·연산 | Class Diagram | Mermaid `classDiagram` 또는 PlantUML `class` |
| 함수/컴포넌트 간 호출·메시지 순서 | Sequence Diagram | Mermaid `sequenceDiagram` 또는 PlantUML `sequence` |
| 알고리즘 처리 흐름 | Activity/흐름도 | Mermaid `flowchart` 또는 PlantUML `activity` |
| 상태전이 상세 | State Machine Diagram | Mermaid `stateDiagram-v2` 또는 PlantUML `state` |
| 구현 단위 간 정적 호출관계 | Call Graph / Component Diagram | Mermaid `flowchart` 또는 PlantUML `component` |
| 설계 요소와 요구/아키텍처 관계 | SysML Requirement Diagram | PlantUML SysML 확장(`<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<trace>>`) |

- **공식 템플릿이 있는 것은 구현 단위 간 UML/호출관계뿐이다(`TPL-SWE3-002`, drawio).** 정식 산출물로
  만들 때는 0.2절 절차에 따라 이 drawio 파일에 클래스/컴포넌트/호출관계를 담는다. Mermaid/PlantUML로
  먼저 초안을 잡은 뒤 drawio로 옮겨도 된다.
- Sequence/State/Activity 등 나머지 UML 다이어그램은 아직 공식 drawio 템플릿이 없으므로, 공식 템플릿이
  제공되기 전까지는 Mermaid/PlantUML 코드블록을 `TPL-SWE3-001`의 해당 장(6장 알고리즘, 8장 상태전이 등)
  본문에 포함하거나 부록으로 첨부한다.
- 다이어그램의 요소 이름(클래스, 함수, 상태 등)에는 설계 ID(0.3절)를 라벨로 병기해 추적이 되게 한다.
- 다이어그램은 보조 수단이다. 다이어그램만으로 설계를 대체하지 않고, 반드시 표의 함수 계약·상태전이
  서술과 함께 제시한다.

## 4. ISO 26262-6 연계 — SW 단위 설계 원칙

안전 관련 설계 요소(상위 요구사항에 ASIL이 부여된 경우)는 ISO 26262-6(SW 단위 설계 및 구현)이 다루는
아래 주제를 설계 서술에 반영했는지 점검한다. **등급별 권고/강력 권고 여부의 정확한 판정은 프로젝트가
보유한 공식 ISO 26262-6 문서를 우선 참조**하고, 이 스킬은 임의로 등급별 세부 기법을 단정하지 않는다.

| 점검 주제 | 설계 서술에서 확인할 내용 |
|---|---|
| 제어흐름의 단순성 | 함수당 단일 진입·단일 종료, 무조건 분기(goto 등) 회피 여부를 2·6절 서술에 명시 |
| 복잡도 제한 | 함수 크기·순환복잡도 상한을 11장 코딩·검증 규칙에 정량 기준으로 명시 |
| 자료·자원 사용 | 동적 메모리 할당, 재귀, 포인터 산술 사용 여부와 제한 근거를 4·13장에 기록 |
| 초기화 및 형 변환 | 변수 초기화 보장, 암묵적 형변환 회피 여부를 4·5절 서술에 명시 |
| 오류·방어 동작 | 입력 유효성, 예외, 자원 실패에 대한 검출·처리·기록을 10장에 기술(2절 예외/오류 처리와 연결) |

- 안전목표/ASIL 근거 자체는 상위 요구사항(`requirements-analyst` 스킬 8절)에서 캐리되며, 이 스킬은
  그 근거를 재생성하지 않고 상위 요구사항 ID를 그대로 인용한다(0.3절 "상위 요구사항 ID").

## 5. 검증방안 — 반드시 실행 가능해야 함(단위시험 연계)

모든 설계 요소(함수 계약, 알고리즘, 상태전이, 정책표)에는 SWE.4(단위검증)에서 실제로 수행 가능한
검증방법을 지정하고, 그 방법의 구체적 절차와 합격기준을 함께 적는다.

| 방법 | 기법 예시 | 의미 |
|---|---|---|
| 화이트박스 단위시험 | 구문/분기/조건 커버리지, 경계값 분석, 동등분할 | 함수 계약의 사전/사후조건을 실제 입력으로 검증 |
| 정적분석 | 린트, 타입체크, 복잡도 측정 | 4절 설계 원칙(복잡도, 형변환 등) 위반 여부 자동 확인 |
| 리뷰(Inspection) | 설계 워크스루, 페어 리뷰 | 함수 계약·알고리즘의 상위 요구/아키텍처 정합성 확인 |

**금지 사항 — 다음과 같은 검증방안을 제시하지 않는다:**
- 정량 기준이 없는 서술(예: "충분히 테스트한다")을 그대로 합격기준으로 사용
- 프로젝트에 실제로 없는 도구·환경(예: 확보되지 않은 커버리지 측정 도구)을 전제로 하면서 가용성을
  확인하지 않은 방법
- 측정/재현이 불가능한 주관적 판단만으로 구성된 방법
- 검증 시점(단위/통합 등 어느 단계에서 수행하는지)이 명시되지 않은 방법

**절차**: 설계 작성 전 프로젝트에 실제로 존재하는 단위시험/정적분석 도구(예: pytest, coverage, 린터,
타입체커 등)를 저장소 설정(`pyproject.toml`, CI 설정 등)이나 사용자 확인을 통해 파악한다. 확인이 안
되면 어떤 도구를 가정했는지 리포트에 명시하고 사용자에게 확인을 요청한다. 그 위에서 실제로 수행 가능한
검증방법과 합격기준을 정한다.

## 6. 일관성 확보

- 명명 규칙(모듈/함수/변수/상태 이름 규칙)과 자료형(4장 공통 자료형)을 문서 전체에서 동일하게
  사용한다.
- 새 설계 요소 작성/수정 시 같은 상위 요구사항·아키텍처 요소에 대해 기존 설계와 모순되는 계약을
  만들지 않는지 대조한다.
- 설계 ID·속성 필드 형식(0.3절 규칙)을 문서 전체에서 동일하게 적용한다.
- 오류 처리·상태 명칭 등 분류 체계를 문서 내에서 일관되게 사용한다.
- 점검 결과 발견된 모순/중복은 별도로 표기하고 해결 전까지 "미해결 갈등"으로 리포트에 남긴다.

## 7. 양방향 추적성 확보 방안

- **ID 체계**: `DES-<모듈/컴포넌트>-<일련번호>`(0.3절). ID는 한 번 부여되면 재사용하지 않는다. 폐기된
  설계 요소는 삭제하지 않고 상태를 "폐기"로 표시해 이력을 보존한다.
- **추적 속성**: 설계 요소마다 `상류 추적(Upstream)`(아키텍처 요소 ID, SW 요구사항 ID)과 `하류
  추적(Downstream)`(소스 파일·함수, 단위시험 ID)을 표 컬럼으로 명시한다.
- **추적성 매트릭스**: 공식 매트릭스는 `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`
  사본, `requirements-analyst` 스킬 0.2/7절)이며, `Architecture ↔ Detailed Design ↔ Code ↔
  SWE.4` 열로 이 스킬의 설계 요소를 연결한다. `TPL-SWE3-001`의 14장("추적성")에는 이 매트릭스의
  위치와 규칙을 요약해 기록하고, 설계 요소가 생성/변경될 때마다 매트릭스를 즉시 갱신한다.
- **SysML 병행 표현**: SysML을 사용하는 경우 `<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<trace>>`
  관계로 추적성을 시각적으로도 표현한다.
- **변경 시 영향분석**: 설계 요소가 변경되면 추적성 매트릭스로 영향받는 하류 산출물(코드, 단위시험)과
  상류 산출물(아키텍처, 요구사항 재검토 필요 여부)을 확인하고, 결과를 개정 이력에 남긴다(추적이 끊긴
  "고아" 항목이 없어야 한다).
- 이 방안은 `aspice-auditor` 스킬의 GP2.2.3(산출물 식별·문서화·형상관리)·GP2.1.3(성과 조정) 점검
  기준과 정합한다.

## 8. 구현 경계와 SBOM/FOSS 라이선스

- `TPL-SWE3-001` 13장("구현 경계")에는 생성 코드, 외부 라이브러리, 플랫폼 종속부와 구현하지 않는
  범위를 명시한다.
- 외부 패키지(특히 오픈소스)를 사용하는 경우, 실제 사용 목록을 0.2절 4단계에 따라
  `ENG-SBOM-001`(`TPL-SBOM-001`)에 기록하고 라이선스 유형·배포 조건(Distribution 컬럼)을 확인한다.
  프로젝트 정책과 충돌하는 라이선스(예: 배포 제약이 있는 카피레프트 라이선스)가 발견되면 임의로
  판단하지 말고 "확인 필요"로 남기고 사용자에게 알린다.
- SBOM 갱신은 설계 변경뿐 아니라 의존성 파일(`requirements.txt` 등) 변경 시에도 함께 수행한다.

## 9. 작업 절차 요약

1. 공식 템플릿 파일 존재 확인 및 등록부 최신 버전·SBOM 등재 여부 확인 (0절)
2. 입력 확인 — 상위 아키텍처(`ENG-SWE2-001`) 요소, 할당된 SW 요구사항(`ENG-SWE1-001`), 기존 설계 ID
   체계 유무 확인
3. 설계 초안 작성 — 함수 계약 패턴(2절), UML/호출관계 다이어그램 병행(3절)
4. ISO 26262-6 단위 설계 원칙 점검(4절, 안전 관련 요소만)
5. 각 설계 요소에 실행 가능한 단위시험 검증방안 부여(5절)
6. 설계 품질 특성(1절) 자가점검 및 일관성 점검(6절)
7. 추적 속성 기록 및 `ENG-TRC-001` 추적성 매트릭스 갱신(7절)
8. 외부 의존성이 있으면 SBOM/라이선스 확인·갱신(8절)
9. 결과를 공식 템플릿 파일(DOCX/DRAWIO/XLSX, 0.2절)에 반영해 출력, 불확실한 부분(상위 근거 미확인,
   검증환경 미확인, 템플릿 버전(v0.9)·SBOM 등록 상태 등)은 리포트 서두에 명시

## 유의사항

- 확인할 수 없는 사항(상위 아키텍처/요구사항 근거, 검증 환경, 공식 표준 문서의 세부 조항)은 추측하지
  말고 "확인 필요"로 남긴다.
- `WP_Templates/`의 공식 산출물 템플릿, 공식 ISO 26262/A-SPICE 문서가 이 스킬의 일반 규칙보다
  우선한다. `TPL-SWE3-001`/`TPL-SWE3-002`는 v0.9(초안)이므로 정식 v1.0이 배포되면 0절의 매핑·절차를
  다시 그 버전에 맞춰 갱신한다.
- `OEM_Sample/OEM-SWR-001_OEM SW 요구사항 사양서.docx`는 교육용 예시이며 상세설계 산출물은 아니지만,
  이 문서의 요구사항 ID(`OEM-SR/FR-###`)를 상위 근거로 인용할 때 참고할 수 있다. 실제 값을 그대로
  베끼지 말고 형식적 참고 자료로만 사용한다.
