# 아키텍처 분석가 (Architecture Analyst)

ISO 26262(기능안전)와 Automotive SPICE 4.1 SWE.2(SW 아키텍처 설계) 프로세스를 준수하는 아키텍처
산출물을 분석·작성하기 위한 방법론이다. 공식 산출물 템플릿이 저장소 `WP_Templates/`에 제공되었으므로,
아래 0절의 템플릿 구조를 그대로 따르고 1~9절은 그 템플릿의 표·절을 채우는 방법론으로만 사용한다. 이
스킬은 `requirements-analyst` 스킬로 작성된 SW 요구사항·Use Case를 입력으로 받고, 그 산출물은
`detailed-design-analyst` 스킬(SWE.3)의 상위 입력이 된다는 전제로 동작한다.

## 0. 산출물 템플릿 (공식 — `WP_Templates/` 기준)

> 아키텍처 작업을 시작하기 전에 **반드시** 아래 파일이 저장소에 실제로 존재하는지 Glob/Read로 먼저
> 확인한다. 존재하면 이 절의 매핑과 절차를 그대로 따른다. 템플릿을 찾을 수 없으면 그 사실을 리포트
> 서두에 명시하고 0.3절의 표 구조만으로 임시 작성한 뒤 "⚠ 공식 템플릿 미발견 — 재구성 필요"를 표시한다.

### 0.1 SWE.2(아키텍처 설계) 산출물 ↔ 템플릿 매핑

| 산출물 ID(등록부 기준) | 내용 | 템플릿 파일 | 형식 | 승인 버전 |
|---|---|---|---|---|
| `ENG-SWE2-001_SW 아키텍처 설계서` | 요소, 책임, 인터페이스, 동적 동작 | `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-001_SW 아키텍처 설계서 템플릿.docx` | DOCX | v1.0 |
| `ENG-SWE2-002_SW 아키텍처 UML 원본` | 아키텍처 요소·인터페이스 UML/SysML 다이어그램 | `WP_Templates/Engineering/SoftwareArchitecturalDesign/TPL-SWE2-002_SW 아키텍처 UML 템플릿.drawio` | DRAWIO | v1.0 |

상위 입력(직접 수정하지 않고 참조만 함): `ENG-SWE1-001_SW 요구사항 명세서`, `ENG-SWE1-002_Use Case
명세서`(`requirements-analyst` 스킬 산출물). 하류 소비자: `ENG-SWE3-001/002`(`detailed-design-analyst`
스킬, 상세설계는 이 문서의 아키텍처 요소 ID를 상위 근거로 인용), SWE.5(통합검증, 11장 통합 전략).
산출물 등록 정보는 `WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`의 "Template Register"
시트에서 확인한다.

### 0.2 파일 사용 절차

1. 템플릿 파일을 복사하고 파일명을 `<산출물 ID>_<산출물명>_<프로젝트/베이스라인>.<확장자>` 형식으로
   바꾼다. 원본 템플릿 파일 자체는 수정하지 않는다.
2. **DOCX(TPL-SWE2-001)**: `docx` 스킬로 열어 표지·변경 이력·작성/검토/승인 상태표를 실제 값으로
   채운다. 각 장 아래 "작성 안내:" 문구는 실제 내용으로 교체하고 안내 문구는 삭제한다. 1~15장 구조(2장
   아키텍처 설계 원칙, 3장 논리 아키텍처, 4장 컴포넌트 책임, 5장 정적 의존성, 6장 인터페이스 명세, 7장
   동적 동작, 8장 상태 전이, 9장 오류 격리와 안전 동작, 10장 품질속성 분석, 11장 통합 전략, 12장
   요구사항 할당, 13장 자원 및 배포 경계, 14장 추적성)는 임의로 바꾸지 않는다.
3. **DRAWIO(TPL-SWE2-002)**: 안내 도형(`boundary`, `actor`, `element`, `edge`, `guide`)을 삭제하고
   실제 소프트웨어 요소·계층, 제공/요구 인터페이스, 의존 방향으로 교체한다. 각 요소 라벨에 요소 ID와
   할당된 요구사항 ID를 병기한다. 검토본·베이스라인 생성 시 PNG도 함께 내보낸다.
4. 표지·저작권 각주는 프로젝트 정책에 따라 유지·교체 여부를 사용자에게 확인하고 임의로 삭제하지 않는다.
5. 채팅 중 빠른 논의·검토용 초안은 이 스킬 1~9절 표기(마크다운 표 + 요소/인터페이스 계약 서술 +
   Mermaid/PlantUML)로 먼저 제시해도 되지만, **정식 산출물(베이스라인 대상)은 반드시 위 공식 템플릿
   파일로 만든다.**

### 0.3 아키텍처 요소·인터페이스 행(표) 공통 속성

TPL-SWE2-001의 관련 장(3·4·5·6·12장) 표에는 최소한 다음 컬럼을 포함한다(등록부의 필수 내용 "요소,
책임, 인터페이스, 동적 동작"을 이 스킬의 품질기준으로 확장한 것):

`요소 ID | 구분(컴포넌트/인터페이스/상태전이/배포노드) | 목적·책임 요약 | 제공 기능 | 소유 책임(팀/역할) |
상위 요구사항 ID(할당) | 정적 의존관계(허용/금지) | 인터페이스 계약(데이터·시간·오류, 해당 시) |
품질속성 대응(ISO 25010 태그) | ASIL/독립성 요구(해당 시) | 하류 추적(상세설계 요소 ID) | 상태`

아키텍처 요소 ID 체계는 `ARC-<계층/서브시스템>-<일련번호>`(예: `ARC-CHILDLOCK-001`)를 기본으로 하되,
프로젝트에 이미 다른 접두어 체계가 있으면 새 체계를 만들지 말고 그 체계를 잇는다. `detailed-design-
analyst` 스킬은 이 ID를 "상위 아키텍처 요소 ID"로 그대로 인용한다.

## 1. 아키텍처 설계 품질 특성 (A-SPICE SWE.2와 정합)

모든 아키텍처 요소는 아래 특성을 만족해야 한다. A-SPICE SWE.2는 아키텍처가 요구사항과 일관되고,
상세설계·통합시험이 가능한 수준으로 구조화되도록 요구한다(정확한 BP 목록은 공식 PAM 참조).

| 특성 | 의미 | 점검 방법 |
|---|---|---|
| 정합성 | 상위 SW 요구사항과 모순되지 않는다 | 각 요소에 상위 요구사항 ID 필드 필수(0.3절) |
| 명확성(모호하지 않음) | 요소 책임·인터페이스 계약이 한 가지로만 해석된다 | 2절의 서술 패턴 사용, 모호어 금지 |
| 완전성 | 모든 SW 요구사항이 최소 하나의 요소·인터페이스에 할당된다 | 12장 요구사항 할당표로 커버리지 확인 |
| 낮은 결합도·높은 응집도 | 요소 간 불필요한 의존이 없고, 요소 내부는 목적이 하나로 수렴한다 | 2·5장의 설계 원칙·정적 의존성 점검 |
| 일관성 | 다른 요소·명명 규칙과 모순되지 않는다 | 7절 일관성 점검 절차 수행 |
| 검증가능성 | 통합시험(SWE.5)으로 인터페이스·동적 동작을 확인할 수 있다 | 6절 참조, 실행 불가능한 검증방법 금지 |
| 추적가능성 | 상위(요구사항)·하류(상세설계·통합시험)와 양방향으로 연결된다 | 8절 추적성 방안 준수 |

## 2. 명확성 확보 — 요소·인터페이스 계약 서술 패턴

모든 아키텍처 요소와 인터페이스는 다음 구조로 서술해 모호함을 없앤다(요구사항 스킬의 EARS, 상세설계
스킬의 함수 계약에 대응하는 아키텍처 버전).

```
요소: <요소 ID/명칭> — <목적>
책임: <이 요소가 소유하는 책임 목록>
입력/출력: <받는 데이터·이벤트> / <내보내는 데이터·이벤트>
오류 처리: <이 요소가 감지·처리하는 오류와 전파 차단 방식>
```

```
인터페이스: <인터페이스 ID> — 제공자 <요소> ↔ 사용자 <요소>
데이터: <필드, 자료형, 단위, 범위>
호출 조건: <동기/비동기, 트리거 조건>
시간 제약(해당 시): <최대 응답시간, 주기>
오류 계약: <오류코드/예외와 호출자 쪽 기대 동작>
```

- "적절히", "충분히", "가능한 대로" 같은 모호어를 쓰지 않는다. 경계값·정량 기준으로 대체한다.
- 상태 전이(8장)는 `<상태>에서 <이벤트/가드>가 발생하면 <전이 동작>을 수행하고 <다음 상태>가 된다`로
  모호함 없이 서술한다(상세설계 수준 상태전이는 `detailed-design-analyst` 스킬 2절에서 이어받는다).
- 요소 하나에는 하나의 응집된 책임 집합만 담는다. 서로 무관한 책임이 섞여 있으면 요소를 분리한다.

## 3. UML/SysML 표현

아키텍처 요소는 표(0.3절)와 요소/인터페이스 계약(2절) 서술에 더해, 이해를 돕는 다이어그램을 포함한다.

| 표현 대상 | 다이어그램 유형 | 권장 문법 |
|---|---|---|
| 요소·계층·인터페이스 개요 | Component Diagram / SysML BDD | Mermaid `flowchart` 또는 PlantUML `component`/SysML `block` |
| 요소 내부 구조·포트 연결 | SysML Internal Block Diagram(IBD) | PlantUML SysML 확장(`block`, 포트/커넥터) |
| 주요 시나리오의 호출 순서 | Sequence Diagram | Mermaid `sequenceDiagram` 또는 PlantUML `sequence` |
| 상태 전이 | State Machine Diagram | Mermaid `stateDiagram-v2` 또는 PlantUML `state` |
| 배포·실행 노드 | Deployment Diagram | PlantUML `deployment` |
| 요구사항 할당 관계 | SysML Requirement Diagram | PlantUML SysML 확장(`<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<allocate>>`, `<<trace>>`) |

- **공식 템플릿이 있는 것은 요소·인터페이스 개요(Component/BDD 수준)뿐이다(`TPL-SWE2-002`, drawio).**
  정식 산출물로 만들 때는 0.2절 절차에 따라 이 drawio 파일에 소프트웨어 요소, 계층, 제공/요구
  인터페이스, 의존 방향을 담는다. Mermaid/PlantUML로 먼저 초안을 잡은 뒤 drawio로 옮겨도 된다.
- IBD/Sequence/State/Deployment 등 나머지 다이어그램은 아직 공식 drawio 템플릿이 없으므로, 공식
  템플릿이 제공되기 전까지는 Mermaid/PlantUML 코드블록을 `TPL-SWE2-001`의 해당 장(7장 동적 동작, 8장
  상태 전이, 13장 자원 및 배포 경계 등) 본문에 포함하거나 부록으로 첨부한다.
- 다이어그램의 요소 이름에는 요소 ID(0.3절)를 라벨로 병기해 추적이 되게 한다.
- 다이어그램은 보조 수단이다. 다이어그램만으로 아키텍처를 대체하지 않고, 반드시 표의 요소/인터페이스
  계약 서술과 함께 제시한다.

## 4. 품질속성 분석 — ISO/IEC 25010 연계

`TPL-SWE2-001` 10장("품질속성 분석")에는 `requirements-analyst` 스킬이 ISO/IEC 25010 특성으로 태깅한
비기능 요구사항(스킬 4절/0.3절)을 아키텍처 결정과 명시적으로 연결한다. 임의로 새 품질특성을 만들지
않고, 상위 비기능 요구사항이 쓰는 특성/부특성 태그를 그대로 이어받는다.

작성 형식(품질속성 시나리오 표): `품질특성(ISO 25010) | 관련 비기능 요구사항 ID | 시나리오(자극-환경-
응답, 정량 기준 포함) | 아키텍처 대응(전술/패턴, 예: 이중화·캐싱·계층분리·타임아웃) | 관련 요소 ID |
검증수준(SWE.5/SWE.6 연계)`

- 비기능 요구사항에 정량 기준이 없으면 아키텍처 대응을 임의로 지어내지 말고 "확인 필요"로 남기고
  상위 요구사항 보완을 요청한다.

## 5. ISO 26262-6 연계 — SW 아키텍처 수준 안전 설계 원칙

안전 관련 요소(상위 요구사항에 ASIL이 부여된 경우)는 ISO 26262-6(SW 아키텍처 설계)이 다루는 아래
주제를 아키텍처 서술에 반영했는지 점검한다. **등급별 권고/강력 권고 여부의 정확한 판정은 프로젝트가
보유한 공식 ISO 26262-6 문서를 우선 참조**하고, 이 스킬은 임의로 등급별 세부 기법을 단정하지 않는다.

| 점검 주제 | 설계 서술에서 확인할 내용 |
|---|---|
| 간섭으로부터의 자유(Freedom from Interference) | 서로 다른 ASIL(또는 ASIL과 QM)이 섞인 요소 간 공간적/시간적 독립성 근거를 5·9장에 기록 |
| 오류 검출·처리 메커니즘 | 오류 감지 위치, 전파 차단, 안전 상태 전이를 9장에 명시(2절 오류 처리와 연결) |
| 중복/다양성(해당 시) | 요구되는 경우 하드웨어·소프트웨어 다양성/중복 설계 근거를 4·9장에 기록 |
| 소프트웨어 파티셔닝 | 파티션 경계와 파티션 간 통신 제어 방식을 6장 인터페이스 명세에 명시 |

- 안전목표/ASIL 근거 자체는 상위 요구사항(`requirements-analyst` 스킬 8절)에서 캐리되며, 이 스킬은
  그 근거를 재생성하지 않고 상위 요구사항 ID를 그대로 인용한다(0.3절 "상위 요구사항 ID").

## 6. 검증방안 — 반드시 실행 가능해야 함(통합시험 연계)

모든 아키텍처 요소·인터페이스·동적 동작에는 SWE.5(통합검증)에서 실제로 수행 가능한 검증방법을
지정하고, 그 방법의 구체적 절차와 합격기준을 함께 적는다.

| 방법 | 기법 예시 | 의미 |
|---|---|---|
| 통합시험 | 인터페이스 시험, 시나리오 기반 통합 순서 시험 | 요소 간 계약(2절)을 실제 통합 환경에서 검증 |
| 정적분석 | 의존성 분석, 순환 의존 검출 | 5장 정적 의존성 규칙 위반 여부 자동 확인 |
| 리뷰(Inspection) | 아키텍처 워크스루, ATAM류 품질속성 리뷰 | 요소·인터페이스의 상위 요구/품질속성 정합성 확인 |

**금지 사항 — 다음과 같은 검증방안을 제시하지 않는다:**
- 정량 기준이 없는 서술(예: "인터페이스가 잘 동작해야 한다")을 그대로 합격기준으로 사용
- 프로젝트에 실제로 없는 도구·환경(예: 확보되지 않은 통합시험 인프라)을 전제로 하면서 가용성을
  확인하지 않은 방법
- 측정/재현이 불가능한 주관적 판단만으로 구성된 방법
- 검증 시점(어느 통합 단계에서 수행하는지)이 명시되지 않은 방법

**절차**: 아키텍처 작성 전 프로젝트에 실제로 존재하는 통합시험/정적분석 환경(빌드/의존성 분석 도구,
통합시험 프레임워크, 스텁/드라이버 여부 등)을 저장소 설정이나 사용자 확인을 통해 파악한다. 확인이 안
되면 어떤 환경을 가정했는지 리포트에 명시하고 사용자에게 확인을 요청한다. 그 위에서 실제로 수행
가능한 검증방법과 합격기준을 정한다(11장 통합 전략과 연결).

## 7. 일관성 확보

- 명명 규칙(요소/인터페이스/상태 이름 규칙)을 문서 전체에서 동일하게 사용한다.
- 새 요소 작성/수정 시 같은 상위 요구사항에 대해 기존 요소와 모순되는 책임·인터페이스를 만들지
  않는지 대조한다.
- 요소 ID·속성 필드 형식(0.3절 규칙)을 문서 전체에서 동일하게 적용한다.
- 품질속성 태그·ASIL 등급 등 분류 체계를 문서 내에서 일관되게 사용한다.
- 점검 결과 발견된 모순/중복은 별도로 표기하고 해결 전까지 "미해결 갈등"으로 리포트에 남긴다.

## 8. 양방향 추적성 확보 방안

- **ID 체계**: `ARC-<계층/서브시스템>-<일련번호>`(0.3절). ID는 한 번 부여되면 재사용하지 않는다.
  폐기된 요소는 삭제하지 않고 상태를 "폐기"로 표시해 이력을 보존한다.
- **추적 속성**: 요소마다 `상류 추적(Upstream)`(SW 요구사항 ID)과 `하류 추적(Downstream)`(상세설계
  요소 ID, 통합시험 ID)을 표 컬럼으로 명시한다.
- **추적성 매트릭스**: 공식 매트릭스는 `ENG-TRC-001_양방향 요구사항 추적 매트릭스`(`TPL-TRC-001`
  사본, `requirements-analyst` 스킬 0.2/7절)이며, `SW Req ↔ Architecture ↔ Detailed Design` 열로
  이 스킬의 아키텍처 요소를 연결한다. `TPL-SWE2-001`의 14장("추적성")에는 이 매트릭스의 위치와 규칙을
  요약해 기록하고, 요소가 생성/변경될 때마다 매트릭스를 즉시 갱신한다.
- **SysML 병행 표현**: SysML을 사용하는 경우 `<<satisfy>>`, `<<verify>>`, `<<refine>>`,
  `<<allocate>>`, `<<trace>>` 관계로 추적성을 시각적으로도 표현한다.
- **변경 시 영향분석**: 요소가 변경되면 추적성 매트릭스로 영향받는 하류 산출물(상세설계, 통합시험)과
  상류 산출물(요구사항 재검토 필요 여부)을 확인하고, 결과를 개정 이력에 남긴다(추적이 끊긴 "고아"
  항목이 없어야 한다).
- 이 방안은 `aspice-auditor` 스킬의 GP2.2.3(산출물 식별·문서화·형상관리)·GP2.1.3(성과 조정) 점검
  기준과 정합한다.

## 9. 작업 절차 요약

1. 공식 템플릿 파일 존재 확인 및 등록부 최신 버전 확인 (0절)
2. 입력 확인 — 상위 SW 요구사항(`ENG-SWE1-001`)·Use Case(`ENG-SWE1-002`), 기존 아키텍처 요소 ID
   체계 유무 확인
3. 논리 아키텍처 초안 작성 — 요소/인터페이스 계약 패턴(2절), UML/SysML 다이어그램 병행(3절)
4. 비기능 요구사항을 품질속성 시나리오로 연결(4절)
5. ISO 26262-6 아키텍처 수준 안전 설계 원칙 점검(5절, 안전 관련 요소만)
6. 각 요소·인터페이스에 실행 가능한 통합시험 검증방안 부여(6절)
7. 설계 품질 특성(1절) 자가점검 및 일관성 점검(7절)
8. 추적 속성 기록 및 `ENG-TRC-001` 추적성 매트릭스 갱신(8절)
9. 결과를 공식 템플릿 파일(DOCX/DRAWIO, 0.2절)에 반영해 출력, 불확실한 부분(상위 요구 미확인,
   검증환경 미확인, 공식 템플릿 미발견 등)은 리포트 서두에 명시

## 유의사항

- 확인할 수 없는 사항(상위 요구사항 근거, 검증 환경, 공식 표준 문서의 세부 조항)은 추측하지 말고
  "확인 필요"로 남긴다.
- `WP_Templates/`의 공식 산출물 템플릿, 공식 ISO 26262/A-SPICE 문서가 이 스킬의 일반 규칙보다
  우선한다. 템플릿이 개정되면(등록부 버전 상승) 0절의 매핑·절차를 다시 그 버전에 맞춰 갱신한다.
- `OEM_Sample/OEM-SWR-001_OEM SW 요구사항 사양서.docx`는 교육용 예시이며 아키텍처 산출물은 아니지만,
  이 문서의 요구사항 ID(`OEM-SR/FR-###`)를 상위 근거로 인용할 때 참고할 수 있다. 실제 값을 그대로
  베끼지 말고 형식적 참고 자료로만 사용한다.
