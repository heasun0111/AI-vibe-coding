# 요구사항 분석가 (Requirements Analyst)

ISO 26262(기능안전)와 Automotive SPICE 4.1(SYS.2/SWE.1 등 요구사항 분석 프로세스)을 준수하는
요구사항 산출물을 분석·작성하기 위한 방법론이다. **초안 상태**이며, 사용자가 제공할 공식 산출물
템플릿이 도착하면 "산출물 템플릿" 절을 그 템플릿으로 교체해야 한다.

## 0. 산출물 템플릿 (미확정 — 임시 골격)

> 공식 템플릿이 대화나 저장소에 제공되기 전까지는 아래 임시 골격을 사용한다. 요구사항 작업을 시작하기
> 전에 **반드시** 공식 템플릿이 제공되었는지 먼저 확인한다. 제공되었다면 그 구조를 그대로 따르고, 이
> 스킬의 체크리스트·방법론은 내용을 채우는 데만 사용한다. 제공되지 않았다면 아래 임시 골격을 사용하되,
> 산출물 서두에 "⚠ 임시 템플릿 사용 — 공식 템플릿 도착 시 재구성 필요"를 명시한다.

임시 골격:

```markdown
# <요구사항 문서 ID> <문서명>

- 버전 / 작성자 / 승인자 / 베이스라인 일자
- 관련 상위 산출물(이해관계자 요구, 안전목표 등)

## 1. 범위 및 용어집
## 2. 기능 요구사항 (표 + UML/SysML 다이어그램)
## 3. 비기능 요구사항 (ISO/IEC 25010 특성별)
## 4. 추적성 매트릭스
## 5. 개정 이력
```

요구사항 한 건의 최소 속성(표 컬럼): `ID | 구분(기능/비기능) | 내용 | 출처(상위요구/안전목표) |
우선순위 | ASIL(해당 시) | 검증방법(I/A/D/T) | 검증 절차·합격기준 | 추적정보(상류/하류) | 상태`

## 1. 요구사항 품질 특성 (ISO/IEC/IEEE 29148, A-SPICE와 정합)

모든 요구사항은 아래 특성을 만족해야 한다. A-SPICE SYS.2/SWE.1은 요구사항이 이 특성들(정확한 BP
목록은 공식 PAM 참조)을 갖추도록 요구한다.

| 특성 | 의미 | 점검 방법 |
|---|---|---|
| 필요성 | 상위 요구/안전목표 등 근거 없이 존재하는 요구사항이 없다 | 각 요구사항에 출처 필드 필수 |
| 명확성(모호하지 않음) | 한 가지로만 해석된다 | 2절의 EARS 패턴 사용, 모호어(적절히/충분히/가능한 한 등) 금지 |
| 완전성 | 필요한 조건·예외가 빠짐없이 기술된다 | 트리거/전제조건/응답을 모두 명시 |
| 일관성 | 다른 요구사항과 모순되지 않는다 | 6절 일관성 점검 절차 수행 |
| 단일성 | 요구사항 하나에 하나의 요구만 담는다("그리고/및"로 여러 요구를 묶지 않음) | "그리고" 등 접속어로 다중 요구가 합쳐졌는지 점검 |
| 실현가능성 | 현재 기술·일정·자원으로 구현 가능하다 | 담당 엔지니어/아키텍트 확인 근거 기록 |
| 검증가능성 | 정량적·객관적 방법으로 참/거짓 판정이 가능하다 | 3~4절 참조, 실행 불가능한 검증방법 금지(5절) |
| 추적가능성 | 상위/하위 산출물과 양방향으로 연결된다 | 7절 추적성 방안 준수 |

## 2. 명확성 확보 — EARS 패턴

모든 기능/안전 요구사항은 다음 5가지 EARS(Easy Approach to Requirements Syntax) 패턴 중 하나로
작성해 모호함을 없앤다.

| 패턴 | 형식 | 사용 시점 |
|---|---|---|
| 상시(Ubiquitous) | `<시스템>은 <응답>을 수행해야 한다.` | 항상 성립하는 요구 |
| 이벤트 기반 | `<트리거>가 발생하면, <시스템>은 <응답>을 수행해야 한다.` | 특정 사건에 대한 반응 |
| 상태 기반 | `<상태>인 동안, <시스템>은 <응답>을 수행해야 한다.` | 특정 상태에서만 유효한 동작 |
| 원치 않는 동작 | `<원치 않는 트리거/조건>이 발생하면, <시스템>은 <안전 응답>을 수행해야 한다.` | 오류/고장 대응, 안전요구사항에 특히 사용 |
| 선택적 기능 | `<기능/옵션>이 포함된 경우, <시스템>은 <응답>을 수행해야 한다.` | 변형(variant)별 요구 |

- "적절히", "충분히", "가능한 한", "즉시(정량 기준 없이)" 같은 모호어를 쓰지 않는다. 정량적 기준(수치,
  단위, 한계값)으로 대체한다.
- 요구사항 하나에는 하나의 트리거·하나의 응답만 담는다. "그리고/및"로 여러 요구가 묶여 있으면 분리한다.

## 3. 기능 요구사항 — UML/SysML 다이어그램

기능 요구사항은 표 형태의 텍스트 서술과 함께, 이해를 돕는 다이어그램을 Mermaid 또는 PlantUML
코드블록으로 문서에 포함한다(렌더링 도구가 필요 없는 텍스트 기반 표기).

| 표현 대상 | 다이어그램 유형 | 권장 문법 |
|---|---|---|
| 액터-기능 개요 | Use Case Diagram | Mermaid(`flowchart`/`graph`로 근사) 또는 PlantUML `usecase` |
| 처리 흐름/알고리즘 | Activity Diagram | Mermaid `flowchart` 또는 PlantUML `activity` |
| 상태 기반 동작 | State Machine Diagram | Mermaid `stateDiagram-v2` 또는 PlantUML `state` |
| 컴포넌트 간 상호작용/시퀀스 | Sequence Diagram | Mermaid `sequenceDiagram` 또는 PlantUML `sequence` |
| 요구사항 간 관계(파생/충족/검증/정제/추적) | SysML Requirement Diagram | PlantUML SysML 확장(`requirement`, `<<deriveReqt>>`, `<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<trace>>`) |
| 시스템 구조/인터페이스 | SysML Block Definition/Internal Block Diagram | PlantUML SysML 확장(`block`, 포트/인터페이스) |

- Mermaid는 GitHub 등에서 별도 도구 없이 렌더링되므로 일반 UML 표현에 우선 사용한다.
- SysML 고유 표기(requirement 다이어그램, BDD/IBD, «satisfy»/«verify» 관계)가 필요하면 PlantUML의
  SysML 확장 문법을 사용한다.
- 다이어그램의 요소 이름(액터, 상태, 블록 등)에는 요구사항 ID를 주석이나 라벨로 병기해 추적이 되게 한다.
- 다이어그램은 보조 수단이다. 다이어그램만으로 요구사항을 대체하지 않고, 반드시 표의 텍스트 요구사항과
  함께 제시한다.

## 4. 비기능 요구사항 — ISO/IEC 25010

비기능 요구사항은 ISO/IEC 25010의 품질특성/부특성 중 해당하는 항목에 명시적으로 매핑하고, 정량적
수용기준을 반드시 포함한다.

| 품질특성 | 주요 부특성 |
|---|---|
| 기능 적합성 | 완전성, 정확성, 적절성 |
| 성능 효율성 | 시간 반응성, 자원 사용성, 용량 |
| 호환성 | 공존성, 상호운용성 |
| 사용성 | 적절성 인식성, 습득성, 운용성, 사용자 오류 보호, UI 심미성, 접근성 |
| 신뢰성 | 성숙성, 가용성, 결함허용성, 회복성 |
| 보안성 | 기밀성, 무결성, 부인방지, 책임추적성, 인증성 |
| 유지보수성 | 모듈성, 재사용성, 분석용이성, 수정용이성, 시험용이성 |
| 이식성 | 적응성, 설치성, 대체성 |

작성 형식 예: `[성능효율성-시간반응성] <조건>에서 <기능>의 응답시간은 <값+단위> 이하여야 한다.`
품질특성/부특성 태그 없이 비기능 요구사항을 작성하지 않는다.

## 5. 검증방안 — 반드시 실행 가능해야 함

모든 요구사항(기능/비기능/안전)에는 검증방법을 아래 4가지 중 하나로 지정하고, 그 방법의 구체적 절차와
합격기준을 함께 적는다.

| 방법 | 기호 | 의미 |
|---|---|---|
| 검사(Inspection) | I | 문서/코드/설계 검토로 확인 |
| 분석(Analysis) | A | 계산, 시뮬레이션, 정적분석 등으로 확인 |
| 시연(Demonstration) | D | 실제/모의 환경에서 동작을 보여 확인 |
| 시험(Test) | T | 정의된 절차와 합격기준으로 실측하여 확인 |

**금지 사항 — 다음과 같은 검증방안을 제시하지 않는다:**
- 정량 기준이 없는 서술(예: "충분히 빠르게", "사용자가 만족해야 한다")을 그대로 합격기준으로 사용
- 프로젝트에 실제로 없는 도구·환경(예: 확보되지 않은 HIL 장비, 실차 시험 인프라)을 전제로 하면서
  가용성을 확인하지 않은 방법
- 측정/재현이 불가능한 주관적 판단만으로 구성된 방법
- 검증 시점(어느 개발 단계에서 수행하는지)이 명시되지 않은 방법

**절차**: 요구사항 작성 전 프로젝트에 실제로 존재하는 개발/테스트 환경(빌드 도구, 정적분석 도구,
시뮬레이터, 테스트 프레임워크, 실차/HIL 장비 여부 등)을 저장소 설정이나 사용자 확인을 통해 파악한다.
확인이 안 되면 어떤 환경을 가정했는지 리포트에 명시하고 사용자에게 확인을 요청한다. 그 위에서 실제로
수행 가능한 I/A/D/T 방법과 합격기준을 정한다.

## 6. 일관성 확보

- 용어집을 유지하고 동일 개념에는 항상 동일 용어를 사용한다(동의어 혼용 금지).
- 새 요구사항 작성/수정 시 기존 요구사항과 같은 조건에서 다른 결과를 요구하지 않는지 대조한다.
- 요구사항 ID·속성 필드 형식(2·4·5·7절 규칙)을 문서 전체에서 동일하게 적용한다.
- 우선순위·ASIL 등급 등 분류 체계를 문서 내에서 일관되게 사용한다.
- 점검 결과 발견된 모순/중복은 별도로 표기하고 해결 전까지 "미해결 갈등"으로 리포트에 남긴다.

## 7. 양방향 추적성 확보 방안

- **ID 체계**: `REQ-<도메인>-<일련번호>` (예: `REQ-SYS-001`, `REQ-SWE-001`, `REQ-NFR-SEC-001`).
  ID는 한 번 부여되면 재사용하지 않는다. 폐기된 요구사항은 삭제하지 않고 상태를 "폐기"로 표시해 이력을
  보존한다.
- **추적 속성**: 요구사항마다 `상류 추적(Upstream)`(이해관계자 요구/안전목표/상위 시스템 요구 ID)과
  `하류 추적(Downstream)`(설계요소 ID, 코드 모듈, 테스트케이스 ID)을 표 컬럼으로 명시한다.
- **추적성 매트릭스**: 문서 4절(또는 임시 골격 4절)에 `요구사항 ID ↔ 상위근거 ↔ 설계 ID ↔ 테스트케이스 ID`
  매핑 표를 별도로 유지하고, 새 산출물이 생성/변경될 때마다 즉시 갱신한다.
- **SysML 병행 표현**: SysML을 사용하는 경우 requirement 다이어그램의 `<<deriveReqt>>`,
  `<<satisfy>>`, `<<verify>>`, `<<refine>>`, `<<trace>>` 관계로 추적성을 시각적으로도 표현한다.
- **변경 시 영향분석**: 요구사항이 변경되면 추적성 매트릭스로 영향받는 하류 산출물(설계/테스트/코드)을
  찾아 갱신 필요 여부를 확인하고, 결과를 개정 이력에 남긴다(추적이 끊긴 "고아" 항목이 없어야 한다).
- 이 방안은 `aspice-auditor` 스킬의 GP2.2.3(산출물 식별·문서화·형상관리)·GP2.1.3(성과 조정) 점검
  기준과 정합한다.

## 8. ISO 26262 연계 (안전요구사항)

- 안전목표(Safety Goal)에서 파생된 요구사항에는 ASIL(QM/A/B/C/D)을 명시하고, 파생 근거(어느
  안전목표/상위 요구에서 왔는지)를 상류 추적 필드에 기록한다.
- 안전요구사항은 "원치 않는 동작" EARS 패턴을 우선 검토해 고장/오류 상황에서의 시스템 응답을 명확히
  기술한다.
- 안전요구사항의 검증방법은 해당 ASIL에서 요구되는 엄격도를 고려해 선정하되(예: 높은 ASIL일수록 시험/
  분석 근거를 더 엄밀하게), 5절의 "실행 가능성" 원칙을 동일하게 적용한다.
- 정확한 ASIL별 권장 기법(예: 특정 분석/테스트 기법의 권고·강력 권고 여부)은 프로젝트가 보유한 공식
  ISO 26262 문서를 우선 참조하고, 없으면 이 스킬은 임의로 등급별 세부 기법을 단정하지 않는다.

## 9. 작업 절차 요약

1. 공식 템플릿 제공 여부 확인 (0절)
2. 범위·이해관계자 요구/안전목표 등 상위 근거 확인
3. 요구사항 초안 작성 — EARS 패턴(2절), 기능은 다이어그램 병행(3절), 비기능은 ISO 25010 매핑(4절)
4. 각 요구사항에 실행 가능한 검증방안 부여(5절)
5. 품질특성(1절) 자가점검 및 일관성 점검(6절)
6. 추적 속성 기록 및 추적성 매트릭스 갱신(7절)
7. 안전요구사항이면 ASIL/근거 기록(8절)
8. 결과를 템플릿(또는 임시 골격) 형식으로 정리해 출력, 불확실한 부분(템플릿 미확정, 검증환경 미확인
   등)은 리포트 서두에 명시

## 유의사항

- 확인할 수 없는 사항(검증 환경, 상위 근거, 공식 표준 문서의 세부 조항)은 추측하지 말고 "확인 필요"로
  남긴다.
