# 좋은 테스트 작성하기

> [obra/superpowers](https://github.com/obra/superpowers)의
> `skills/test-driven-development/writing-good-tests.md`를 이 프로젝트(Python/`unittest`)에 맞게
> 각색했다. [SKILL.md](SKILL.md)의 4절(긍정/부정 케이스, Doxygen 목적 서술)과 함께 적용한다.

**불러오는 시점**: 테스트를 작성·수정할 때, mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를
추가할 때.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재한다. 아래 두 원칙이 모든 것을 지배한다.

```
1. 모든 테스트는 자신이 잡는 깨짐을 명명한다
2. 모든 테스트는 진짜 대상을 실행한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다: 먼저 작성되어 실제 코드에 대해 실패하는 것을 본 테스트는
이미 실패할 수 있음을 증명했고, 실제 의존성이 느리거나 외부적일 때만 mock을 쓸 자격을 얻는다.

## 원칙 1: 깨짐에 이름 붙이기

테스트 본문을 쓰기 전에 답한다: **어떤 프로덕션 변경이 이 테스트를 실패하게 만드는가 — 그리고 그
변경은 버그인가, 의도된 결정인가?** 테스트는 잘못된 분기, 빠진 부작용, 잘못된 인자, 경계 케이스, 깨진
계약을 잡을 때만 존재할 가치가 있다.

**기대값은 독립적으로 도출한다.** 리터럴과 손으로 검산한 fixture를 쓴다. 테이블 기반 테스트에서
리터럴 `want` 값을 쓰는 형태를 선호한다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 코드가 무엇을
하든 항상 통과한다.

```python
# ❌ 거울 단정(mirror assertion): 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
assert buildSearchQuery({"tag": "urgent"}) == expected

# ✅ 손으로 도출한 리터럴
assert buildSearchQuery({"tag": "urgent"}) == 'tag:"urgent"'
```

**변경 감지기(change detector)를 만들지 않는다.** 의도된 결정만 실패시킬 수 있는 테스트(상수 값,
정확한 메시지 문구, 내부 구조 등)는 재설계할 때마다 울리고 버그에는 잠들어 있다. 결정에 의존하는
행동을 테스트한다: `assert MAX_RETRIES == 5`가 아니라 "실패한 호출은 5번 재시도되고 6번째 시도는
일어나지 않는다"를 검증한다.

**텍스트가 아니라 동작을 검증한다.** 스크립트·스킬·설정 파일이 특정 줄을 포함하는지 단정하는 것은
소스가 소스라는 것만 증명한다. 스크립트는 통제된 입력으로 실행해 출력·부작용·종료 코드를 단정한다.
에이전트에게 지시하는 문서는 그 문서를 소비하는 에이전트의 동작으로 검증하고(`writing-skills` 참고),
사람이 읽는 산문은 테스트 대상이 아니다.

**프레임워크가 아니라 우리 코드를 검증한다.** 우리 코드가 경계에서 맺는 계약(등록하는 라우트, 내보내는
쿼리, 만들어내는 페이로드)을 테스트한다. 상위 라이브러리의 동작은 그 라이브러리 유지관리자의 테스트
몫이다(대표 사례: 우리 라우터가 등록된 핸들러를 호출하는지 단정하는 것 — 이건 프레임워크의 테스트지
우리 테스트가 아니다). 상위 동작이 정말 예상과 달랐다면, 그 가정을 명명하는 좁은 특성화(characterization)
테스트 하나만 작성한다. 이 경계는 우리 코드 내부에도 적용된다: 생성자, getter, 상수, 단순 위임은 값을
검증·정규화·기본값 설정·도출·강제하거나 부작용을 일으킬 때만 테스트 대상이며, 그렇지 않으면 그것에
의존하는 첫 번째 소비자-가시적 결과를 단정한다.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만들 프로덕션 변경을 명명한다.

  하나도 명명할 수 없다면        → 관찰 가능한 동작 중심으로 재설계
  "소스 텍스트가 바뀌었다"        → 그 산출물을 실행해 효과를 단정
  의도된 결정만 해당한다면        → 변경 감지기다; 그 결정에 의존하는 동작을 테스트

  기대값이 검증 대상 코드 없이 도출됐는지 확인한다.
  그 코드의 로직이나 헬퍼를 재사용했다면:
    리터럴 또는 손으로 검산한 fixture로 바꾼다
```

## 원칙 2: 진짜 대상을 실행하기

**mock 자체는 아무 단정도 받을 자격이 없다.** mock이 존재하면 통과하고 없으면 실패하는 단정은 그
컴포넌트에 대해 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 단정한다. mock을 검증하고 있다면
mock을 풀거나 그 단정을 삭제한다.

```python
# ✅ 실제 동작
self.assertTrue(navBar.isRendered())

# ❌ mock 존재 여부
self.assertTrue(sidebarMock.called)
```

**"우리가 mock의 동작을 테스트하고 있는 건 아닌가?"**를 늘 자문한다.

**올바른 층에서 mock한다.** 실제 메서드의 모든 부작용을 파악한 뒤, 느리거나 외부적인 동작만 mock하고
테스트가 의존하는 나머지는 실제로 둔다. 확신이 없으면 먼저 실제 구현으로 테스트를 돌려 무엇이 실제로
필요한지 관찰한다.

```python
# ❌ mock이 중복 검출 로직이 읽는 설정 파일 쓰기를 삼켜버림
with patch("tool_catalog.discover_and_cache_tools", return_value=None):
    ...

# ✅ 느린 서버 기동만 mock하고, 설정 파일 쓰기는 실제로 둠
with patch("mcp_server_manager.MCPServerManager"):
    ...
```

**더블을 구체적으로 만든다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단정한다 — 아무 값이나
받아주는 fake는 아무것도 검증하지 못한다. 각 분기(성공/오류/잘못된 입력)마다 별도의 fixture나 spy를
주어, 잘못된 분기가 기대값을 만족시키지 못하게 한다.

**실제 데이터를 완전히 반영한다.** 실제로 존재하는 전체 구조(문서화된 모든 필드)를 mock하고, 테스트가
읽는 필드만 mock하지 않는다. 부분적인 mock은 하류 코드가 빠뜨린 필드를 읽을 때 조용히 실패한다 —
테스트는 통과하지만 통합은 깨진다.

**프로덕션 클래스는 프로덕션 메서드만 가진다.** 테스트에서만 필요한 정리(cleanup)는 프로덕션 클래스의
`teardown()` 같은 메서드가 아니라 테스트 유틸리티에 둔다. 자문한다: 이 메서드는 테스트에서만
호출되는가? 이 클래스가 이 자원의 생명주기를 소유하는가? 답이 "그렇다"가 아니면 → 테스트 유틸리티로.

**복잡한 mock보다 실제 컴포넌트를 우선한다.** mock 준비가 테스트 로직보다 커지거나, mock이 실제
컴포넌트에 있는 메서드를 놓치거나, mock이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 쓰는 통합
테스트로 바꾼다. **"여기서 정말 mock이 필요한가?"**를 자문한다.

### 게이트 함수

```
mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 둔다.
  느리거나 외부적인 그 아래 층만 mock한다.

  mock 응답이 실제 구조를 완전히 반영하는가.

  테스트만 호출하는 메서드는 프로덕션이 아니라 테스트 유틸리티에 있는가.

  mock 자체를 단정하려 하고 있는가?
    mock을 풀거나 그 단정을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 순환 — 실패하는 테스트, 최소 구현, 리팩터링 — 이 곧 "완료"의 정의다. 동작이 필요로 하는 테스트만,
그만큼만 만든다: 자명한 코드와 사람이 읽는 산문은 테스트가 필요 없고, 절차를 만족시키기 위해서만 쓴
테스트는 영원히 유지보수 비용이 된다.

## 뮤테이션 점검

끝내기 전에, 머릿속으로 프로덕션 코드를 변형(mutate)해 본다. 현실적인 변형마다 최소 하나의 테스트가
실패해야 한다.

- 잘못된 상수나 인자
- 잘못된 분기 처리
- 빠진 상태 변화나 부작용
- 빈 값이나 기본값 반환
- 0, 빈 값, None, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

어떤 변형도 잡아내지 못한다면 그 동작은 보호되지 않은 것이거나, 그 테스트가 항진명제(tautology)라는
뜻이다.

## 빠른 참고

| 상황 | 할 일 |
|---|---|
| 테스트를 작성할 때 | 그것이 잡는 깨짐을 명명한다 — 버그지 결정이 아니다 |
| 기대값을 만들 때 | 손으로 도출한다; 검증 대상 코드로 만들지 않는다 |
| 스크립트나 문서를 테스트할 때 | 실행하거나 그 소비자를 압박 테스트한다; 텍스트를 grep하지 않는다 |
| 의존성 테스트를 쓰려 할 때 | 그들의 문서화된 동작이 아니라 우리 쪽 경계 계약을 테스트한다 |
| mock된 요소를 단정하려 할 때 | 실제 컴포넌트를 테스트하거나 mock을 푼다 |
| 메서드를 mock하려 할 때 | 부작용을 파악하고, 느리거나 외부적인 층만 mock한다 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트만 쓰는 정리가 필요할 때 | 테스트 유틸리티에 둔다 |
| mock 준비가 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 바꾼다 |
| 테스트 파일을 끝낼 때 | 뮤테이션 점검을 수행한다 |

## 경고 신호

- 준비(setup)와 단정이 같은 객체를 공유해 항상 같아지도록 보장한다
- 테스트가 패닉·크래시·셀렉터 없음으로만 실패할 수 있다
- 의도된 변경마다 실패하고, 실제 결함에는 절대 실패하지 않는다
- 기대값이 반복문·빌더·헬퍼 뒤에 숨어 있다
- 테스트가 소스 텍스트를 grep 하거나, 제거된 심볼이 계속 없는지만 단정한다
- 프레임워크만 남아도 여전히 통과할 테스트다
- 커버리지만을 위해 존재하고 어떤 부작용·결과도 확인하지 않는다
- `*-mock` 같은 테스트 ID를 단정하거나, mock을 제거하면 실패한다
- 어떤 메서드가 테스트 파일에서만 호출된다
- mock 준비가 테스트의 절반을 넘거나, 그 mock이 왜 필요한지 설명할 수 없다
- "혹시 몰라서" mock을 건다
