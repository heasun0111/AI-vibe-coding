# SW 시스템 테스트 케이스 생성

## 개요

SW 요구사항 명세서 기반으로 SW 시스템 테스트 케이스를 생성하기 위한 방법론 스킬입니다. 이 스킬은 "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지에 대한 방법론만 정의합니다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(예: `sw-system-tester` 서브에이전트)가 수행합니다.

이 스킬은 Automotive SPICE의 **SWE.6(소프트웨어 검증)**에 해당한다 — SW 전체를 완성된 산출물로 보고
요구사항 기준으로 블랙박스 검증한다. 컴포넌트 **간** 인터페이스·호출 경로의 화이트박스 검증(Function/
Call 커버리지)은 `integration-test-analyst` 스킬(SWE.5)의 범위이고, 함수 **내부** 분기 검증(Branch
커버리지)은 `tdd` 스킬(구현 단계)의 범위다 — 이 스킬은 그 둘을 다시 정의하지 않는다.

## 공식 산출물과 등록부

이 스킬의 산출물은 A-SPICE 산출물 등록부(`WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx`)의
SWE.6 항목에 해당한다.

| 산출물 ID(등록부 기준) | 템플릿 파일 | 형식 | 승인 버전 |
|---|---|---|---|
| `ENG-SWE6-001_SW 검증 명세서` | `WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-001_SW 검증 명세서 템플릿.xlsx` | XLSX | v1.0 |
| `ENG-SWE6-002_SW 검증 결과서` | `WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-002_SW 검증 결과서 템플릿.xlsx` | XLSX | v1.0 |

공식 템플릿의 기본 컬럼은 `TPL-SWE6-001`(Verification Specification 시트: `Test ID | SW Req |
Level/Environment | Stimulus | Expected Result | Technique | Execution`)과 `TPL-SWE6-002`
(Verification Results 시트: `Test ID | SW Req | Result | Actual Result | Evidence Locator |
Execution Time | Scope Note`)이다. 정식 산출물을 만들 때는 이 두 파일을 복사해 기반으로 삼고
(원본은 수정하지 않는다), 아래 "산출물 구조"의 추가 요소(비기능 그룹핑, 확정 근거)는 공식 컬럼을
지우거나 이름을 바꾸지 않고 **덧붙이는 방식**으로 반영한다:

- `SW Req` 컬럼에는 `requirements-analyst` 스킬이 부여한 요구사항 ID를 그대로 인용한다(비기능
  요구사항은 이미 `REQ-NFR-...` 형식과 `[품질특성-부특성]` 태그를 갖고 있으므로, 이 값으로 기능/비
  기능과 품질특성을 구분할 수 있다 — 별도 분류 체계를 새로 만들지 않는다).
- 비기능 테스트 케이스를 모아보는 용도의 "비기능 테스트 케이스" 시트는 `TPL-SWE6-001`에 추가하는
  **보조 시트**로 두고(공식 시트는 그대로 유지), `SW Req`로 원본 행과 연결한다.
- "확정 근거"는 `TPL-SWE6-001`의 `Expected Result` 셀 끝에 괄호로 덧붙이거나(예: `... (확정:
  2026-03-05, 승인자 OOO)`), 별도 "확정 근거" 컬럼을 공식 컬럼 뒤에 추가해 기록한다 — 어느 쪽이든
  기록 위치를 문서 서두에 명시한다.
- `ENG-TRC-001` 양방향 추적 매트릭스(`requirements-analyst` 스킬 0.2/7절)의 `SWE.6` 열에 이 스킬의
  `Test ID`를 반영해야 함을 사용자 또는 담당 에이전트에게 알린다.

## 기반지식

- **ISO 26262 Part 6**: 소프트웨어 테스트 전반에 대한 요건 중 이 스킬은 시스템(SW 전체) 수준 부분을 적용합니다. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 합니다. 인터페이스 시험·결함 주입·자원 사용량 시험 등 컴포넌트 통합 수준 기법은 `integration-test-analyst` 스킬(SWE.5)이 다룹니다.
- **A-SPICE SWE.6**: 소프트웨어 검증(완성된 SW를 요구사항 기준으로 검증) Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구합니다. SWE.4(단위)는 `tdd` 스킬, SWE.5(통합)는 `integration-test-analyst` 스킬이 각각 담당합니다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의 품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 그룹화합니다.

## 적용 대상 테스트 기법

요구사항의 성격에 맞춰 아래 기법 중에서 선택하여 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시합니다.

- **경계값 분석**: 검증기준에 수치·범위·임계값이 있는 경우, 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출합니다.
- **동치 클래스(동등분할)**: 입력 도메인을 유효/무효 클래스로 나누어 대표값을 도출합니다.
- **조합 테스트(전 조건 조합)**: 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 우선 적용합니다.
- **페어와이즈**: 조건·값의 조합 수가 많아 전수 조합 테스트가 비현실적인 경우에 대체 적용합니다.
- **엣지 케이스**: 정상 범위의 극단, 동시성/타이밍 등 일반 분석 기법으로 포착되지 않는 특이 조건을 다룹니다.
- **경험 기반 테스트**: 유사 시스템의 결함 이력이나 QA 경험에 근거해 오류를 추정합니다(오류 추정, 탐색적 테스트 등).

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수합니다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 구조

산출물 파일과 시트/컬럼 구조는 "공식 산출물과 등록부" 절을 따른다(중복 정의하지 않음). 요약하면:
공식 `Verification Specification`/`Verification Results` 시트를 기본으로 채우고, 비기능 케이스는
`SW Req`로 원본과 연결되는 보조 시트에 ISO 25000 품질 특성별로 모아 보며, 확정 근거는 그 절에서 정한
위치(덧붙인 컬럼 또는 `Expected Result` 괄호 표기)에 기록한다.
